# Document manifests and fixed bodies

Approved design, 2026-10-03. This supersedes the descriptive metadata overlay
and identity/applicability adoption mechanisms. Existing test data does not
require migration. Fixtures and host test stores are refreshed outside the
application; there is no pre-ID upgrade-on-edit path. There is one save path for all editable metadata.

## A document has one identity, one body, and complete manifest revisions

```text
Document doc-7f32                  stable within its owning pod
|
+-- Blob B1                        unchanged file bytes
|
+-- Manifest M1                    original metadata
+-- Manifest M2                    corrected description
+-- Manifest M3 <-- current        renamed document / corrected applicability
```

Every new registration gets a stable `document_id`. Each complete manifest
contains that ID, a `previous` manifest digest (null initially), all metadata,
and the existing `files` descriptor with the fixed blob hash, size, and path.
New manifests use `caiman.document.v4`. Manifest hashes identify revisions;
the human-facing `version` field remains an opaque editable label. A metadata
correction does not require changing that label.

Name, version, description, issuer, part/program, document type, silicon
revisions, source, and converter all follow the same save process. Pod, document
ID, file descriptors, original filename, ingestion timestamp, and pipeline
information remain system-controlled. History links are generated by the save
service. No-op edits write nothing. Identical re-imports reuse registration.

## References pin bodies and follow approved metadata

```text
Old board -----+
New board -----+--> {pod, document, blob} --> current manifest --> fixed blob
Project -------+
Collection ----+
```

Stored document selectors carry stable `pod`, `document`, and `blob` values.
Notes and feature requirement IDs remain properties of their references.
Human-readable refs and manifest digests may be used to select a document at
authoring time; saving resolves them to its stable ID and blob. They are not
its continuing identity. Board/project references to boards still pin exact
board manifest digests.

Normal views, including documents opened through old boards, resolve the
latest approved complete manifest. Resolution verifies document ID, pinned
blob, content hash, and size. Missing dependencies or a changed body are errors.
Board/project/collection snapshots do not change merely because document
metadata changed. Explicit manifest reads and history return stored revisions.
A configuration digest fixes its declarations and document bodies, not the
current metadata displayed for those documents.

Each document is independent even when two documents contain identical bytes.
Changed file bytes require a new document registration and explicit replacement
of references. A name/version collision in the same catalog location remains
an error; rename the new document or use a distinct version label.

## Flexible attachments

Users decide which documents belong on boards and parts. Do not compare a
document's issuer to the vendor, its part to the board/part name, or its silicon
revisions to the board's revision. Documents declaring a program can also be
attached. These metadata fields describe the document; they do not restrict
attachments. Document attachments do not require a board-level vendor.

Keep field type/format and required-field checks, catalog collision checks,
reference and blob integrity checks, and stale-review protection. A feature's
governing document must still belong to its project's document set.

## Reviewed save

```text
Open current manifest
         |
Edit any metadata
         |
Validate formats and unchanged body -- invalid --> explain field error
         |
Review diff and known local usages ---- cancel --> no writes
         |
Approve
         |
Recheck reviewed state ---------------- stale ---> review again
         |
Write complete immutable manifest
         |
Publish current pointer and catalog refs together
         |
All references see approved metadata; same body
```

Review explains that metadata changes affect every reference, including old
boards. Usage enumeration lists current named local roots and indirect project
usages through pinned boards. It does not claim to enumerate all historical
snapshots or unavailable clones. An incomplete usage scan is reported but does
not block an otherwise valid edit. Changes to the review's known usages or
metadata require a fresh review. Usage discovery never writes configurations.

Saving is local; other clones receive changes through explicit owning-pod Git
Sync. No dependent-pod updates or automatic pushes are required for metadata edits.

## Storage and publication

```text
<pod>/
  blobs/sha256/...                  immutable body bytes
  manifests/sha256/...              complete immutable manifest revisions
  refs/document-heads/<document>    current manifest digest
  refs/documents/<catalog-path>     current manifest digest, for named discovery
```

There are no metadata overlays or separate description/provenance objects.
A rename moves the catalog entry but leaves the stable document head and all
consumer references intact. Both refs point to the same complete manifest.

Under the existing store writer lock, recompute the proposal, write immutable
objects, then journal and publish head/catalog changes. Readers reject an
in-progress transaction. Failed or interrupted publication restores old refs;
new immutable objects may remain unreachable. The store's existing transaction
recovery and per-pod Git writer exclusion apply to registration and edits.

## History and restoration

History follows `previous` from the current manifest and validates that every
revision has the same document ID and file descriptor. Raw digest reads do not
follow the current pointer. Restoring metadata copies an earlier revision's
editable fields into a new reviewed edit; it never rewinds or deletes history.
The document editor's **Metadata History** section lists saved revisions newest
first. Expand a revision to read its metadata and complete manifest JSON; Current
and Original markers identify its place in history. Browsing is read-only and
preserves unsaved edits. Restoration is not yet exposed in the UI.

## Verification

Tests cover all-field full revisions, old board/project/collection resolution,
rename continuity, independent equal-byte documents, unchanged consumer hashes,
flexible attachments, history, changed-body rejection, incomplete usage scans,
stale reviews, transaction rollback/recovery, and explicit pod Sync. Editor
checks cover review/cancel/save and truecolor, 256-color, and 16-color modes.
